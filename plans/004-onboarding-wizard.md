## Why this matters

The adopting domains (Students, Parents, Platform/EduPass) are explicitly **not AI-native**: no one there will author skills or hand-edit YAML. The agreed adoption bar (requirements R7–R8, acceptance AE2): a person who knows only "our primary colour and our fonts" installs the plugin, runs one skill, answers plain-language questions, and ends with a valid, working product context — every unanswered field falling back to foundation defaults. Today's setup skill installs per-user tools and only "optionally seeds a DESIGN.md"; this plan makes the interview the centrepiece. The wizard is the "during" half of one story whose "before" half is the website onboarding page (plan 006, R13) — the two must describe the same steps in the same order with the same names.

## Steps

### Step 1: Restructure the skill around three entry modes

Read both existing setup files fully. Restructure into: **Mode A — set up my machine** (existing tool checklist, unchanged content); **Mode B — onboard my product** (the new interview, below); **Mode C — orient me** (existing newcomer orientation). SKILL.md description gains Mode B language: "onboard a product to the standard — interview you for your brand basics and write your product's design context — no file editing needed". Keep all existing routing cues and NOT-for clauses.

**Verify**: `grep -n 'onboard my product\|interview' harness/.claude/skills/setup/SKILL.md` → present.

### Step 2: Write the interview

The interview (in `setup.md` or a new `interview.md`) is a scripted conversation the agent conducts. Requirements:

- **Plain language, one question at a time**, never assuming YAML/git knowledge. Every question shows an example answer and an explicit "skip — use the standard's default" option.
- Question order: product name → which domain (offer the four from `standards/domains/`, describe each in one line) → audiences (from catalog vocabulary, plain-language descriptions) → primary colour (accept a hex or "we have a token") → typefaces (display + body; skip = foundation default) → stack (free text; skip allowed) → illustration direction + SREF codes (skip allowed) → voice/tone pointer (skip allowed).
- **Answers map 1:1 to DESIGN.md sections** per DESIGN-CONTEXT.md; a skipped question writes **nothing** (absent = default — never write placeholder values).
- After the interview: write `DESIGN.md` at the adopter repo root; run `generate-design-json.py`; show the user the generated `.dxd/design.json` and read back their choices in plain language ("Your primary is #0A7B4B; anything you skipped uses the standard's defaults").
- If the chosen domain's profile is a `proposed` stub, tell the user their answers can seed the domain profile: draft the YAML snippet (from `_template.yaml`) and instruct them to send it to the foundation owner via the ratchet (link `harness/CONTRIBUTING.md`) — do not write into `standards/domains/`.
- Include the guardrail from DESIGN-CONTEXT.md verbatim: parameters only, never rule restatements — the wizard writes values, not prose rules.

**Verify**: dry-run the script yourself against the AE2 persona (knows only primary colour + font names): walk each question, confirm every non-brand question is skippable, and the resulting DESIGN.md parses — run the generator round-trip command → `.dxd/design.json` contains exactly the answered keys.

### Step 3: Reconcile the two onboarding docs

`harness/docs/ONBOARDING.md` (repo-level adoption): its DESIGN.md-seeding section now delegates to "run `/dxd:setup` → onboard my product"; keep the repo-level concerns (manifest, record locations, L1 approver) that the wizard doesn't cover, and state the split explicitly at the top ("this doc = your repo and team; the setup wizard = your machine and your product's brand context").

**Verify**: `grep -n 'setup' harness/docs/ONBOARDING.md | head` → delegation present; no step-by-step DESIGN.md authoring instructions remain duplicated.

### Step 4: End-to-end rehearsal record

In a temp dir, simulate the full Mode B path as the AE2 persona (answer only name/domain/colour/fonts, skip the rest); save the transcript of questions, the produced DESIGN.md, and the generated JSON into the PR description. This is the acceptance evidence for R8.

**Verify**: generated JSON has `domain`, `colour`, `typography` keys and nothing else; `python3 harness/checks/validate.py` (in this repo) still exits 0.
