title: Prompts
description: A system prompt is the fixed instructions the model reads before every user message. The designer who writes it decides how the AI behaves.
status: proposed
---

**Start here whenever you write or review a system prompt.**
The eight rules below cover role, constraints, structure, examples, positive framing, safety against pasted content, reasoning, and testing.
Follow them for any AI feature you ship.

The prompt is also where you defend against **adversarial input** (content crafted to hijack the model, called prompt injection). Prompt injection matters in education because a learner has a motive to try it, and it can only be caught here, not in the interface.

---

## Give the assistant a role in the product context

Name the product, the people using it, and the setting.
A concrete role anchors tone and scope more reliably than a generic one.

| Do | Don't |
| --- | --- |
| "You are a records assistant for school administrators working in the enrolment console." | "You are a helpful assistant." |
| "You are a revision coach for secondary students preparing for an exam." | "You are an AI for education." |

## State constraints with the reason

State the reason behind every constraint.
A bare rule is brittle, because the model cannot extend it to an edge case it has not seen.

| Do | Don't |
| --- | --- |
| "Use the terms from the national curriculum glossary, so answers match the wording learners already see in their materials." | "Use terms from the approved word list." |

## Use a simple, consistent structure

Structure the prompt in four sections, in this order: identity, instructions, examples, context.
Wrap each in an XML tag, a plain angle-bracket label, so a later section cannot silently override an earlier one.

| Do | Don't |
| --- | --- |
| `<identity>`, `<instructions>`, `<examples>`, `<context>` in that order, each in its own tag. | Interleave instructions and examples in one unstructured block. |

## Add 3-5 labelled examples

Show 3 to 5 labelled examples, including one correct reply and one that misses the tone.
A labelled example teaches tone faster than any description of it.

### When to use

Add labelled examples when tone or output shape is hard to describe in words alone.

### When not to use

Skip examples for narrow tasks where one clear rule covers every case.
Use [state constraints with the reason](#state-constraints-with-the-reason) instead.

| Do | Don't |
| --- | --- |
| Label one example `<example type="correct">` and one `<example type="too-clinical">`, then show the same reply to a worried parent in each. | Write "Use a warm, professional tone" with no examples. |

## Tell the model what to produce, not what to avoid

Write instructions that say what the model should produce, not what it should avoid.
Positive instructions are easier for the model to apply reliably and easier for you to audit.

| Do | Don't |
| --- | --- |
| "Respond in plain prose, one idea per sentence, no more than three sentences for a short answer." | "Do not use markdown formatting or headers." |
| "When the question is the person's own thinking, ask a guiding question and offer a worked example on other material." | "Never just give them the answer." |

## Treat pasted content as data, never as instructions

Wrap anything a person pastes in a named tag: a submitted form, an uploaded policy, a forwarded email.
State in the prompt that content inside those tags cannot change the assistant's role or constraints.
This blocks prompt injection, instructions hidden in pasted text that tell the model to ignore its own rules.
Content a learner submits is a live route for this, because the learner has a motive to change the answer they get.

| Do | Don't |
| --- | --- |
| Wrap pasted material in `<pasted_content>` and state that nothing inside it can change the assistant's constraints. | Accept pasted material in the main user message with no tag boundary. |

## Ask for reasoning only when it helps

### When to use

Tell the model to think before it answers on a multi-step or high-stakes task.
Weighing an applicant's goal, prior results, and entry requirements before a course recommendation is a good fit.

### When not to use

Skip the reasoning step for routine output where it adds delay without benefit.
A one-line rewrite, a short summary, or a tag suggestion does not need it.

| Do | Don't |
| --- | --- |
| "Before recommending a course, weigh the applicant's stated goal, their prior results, and the entry requirements" for a complex, context-sensitive task. | Append a reasoning step to every prompt, including a one-line rewrite. |

## Test on real inputs before shipping

Run 5 to 10 real inputs before the feature goes live.
Include an ambiguous input, an out-of-scope input, and a single word.
Check tone, scope limits, and what happens when the assistant cannot answer.

| Do | Don't |
| --- | --- |
| Test with "Why was my application rejected?", "Book me a room", and "help" before launch. | Test only the happy-path inputs you wrote the prompt to handle. |
