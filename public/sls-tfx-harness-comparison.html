tf TFX design harness / standards

Internal architecture comparison · revised 27 July 2026

Same ambition, different abstraction.

SLS turns one repository’s design-system facts into a deterministic production workflow. TFX turns portfolio design intent into portable controls, visual evidence and informed judgement. SLS is deeper locally today; TFX is broader across products. The best outcome combines them.

SLS strength: repository conformance TFX strength: portable design quality Recommendation: shared intent, explicit local bindings

Based on the public SLS knowledgebase and Storybook, the current TFX Design Standard repository, and the 27 July design-team discussion. The meeting informs the interpretation; published artefacts remain the evidence for technical claims. The private SLS source and live skill files were not reviewed.

01 / The distinction

The difference is where the rule lives

Both systems can guide an agent from request to working UI. Their current centres of gravity sit at different abstraction levels.

Concept and portfolio layer

TFX source of truth: the control catalog

States the outcome, severity, scope and verification mode. Product manifests supply local facts.

  • Portable across products, audiences and surface types
  • Design spans accessibility, layout, content, motion, identity and flow
  • Deterministic, judgement and hybrid verification
  • Visual journey evidence and an independent evaluator
Portable intent ↔ local facts

Implementation and repository layer

SLS source of truth: the working system

Reads SLS tokens, components, commands and delivery paths, then repeats the current workflow reliably.

  • Direct edits to real token and component packages
  • Concrete Storybook and application previews
  • Tests, snapshots, visual regression and green gates
  • Merge-request environments and production exclusion

A useful shorthand: SLS primarily asks, “Did the result conform to this implementation?” TFX primarily asks, “Did this rendered journey satisfy the intended experience and shared controls?” Both systems contain some of the other mode.

02 / How quality is proved

One checks conformance; one judges the journey

This is not a choice between code checks and visual judgement. A mature harness needs both, applied to the right object.

Implementation × deterministic

SLS is strongest here

The repository can answer precise questions because its packages and commands are known.

  • Token and component conformance
  • Stories, tests and builds
  • Current green-gate checks

Implementation × visual

SLS also renders the work

Storybook, snapshots, previews and visual regression catch failures that source inspection misses.

Portable control × deterministic

TFX establishes the floor

Scripts and scanners run first. L0 blocks; L1 failures return the agent to implementation.

Portable intent × judgement

TFX is strongest here

The agent captures widths, states and the recovery path. A separate evaluator grades the rendered journey against the sprint contract.

Important correction to the meeting shorthand: in TFX, tier and check type are separate axes. L0, L1 and L2 describe enforcement and waiver strength. Deterministic, judgement and hybrid describe how a control is verified. TFX can therefore carry an L1 judgement control or an L2 deterministic control.

04 / Scalability

Both can scale. They scale in different directions.

The fair comparison is what each architecture reuses today, not a claim about either team’s theoretical ceiling.

SLS scales through local certainty

It can add packages, commands, domain guidance and skills while preserving exact repository behaviour.

  • Fastest route to reliable SLS implementation
  • High confidence when the correct answer already exists in code
  • Can extend beyond components if its knowledgebase and skills expand
  • Risk: shared design rules become duplicated local policy

TFX scales through portable intent

It can add domain skills against one catalog, then calibrate them through product and audience scope.

  • Reuse across different products and maturity levels
  • Deterministic floors coexist with model and human judgement
  • Design disciplines can grow without creating new rulebooks
  • Risk: abstract controls stay manual or drift from local code

Revised verdict: TFX has the stronger cross-product scalability model today. SLS is not inherently unscalable; its present architecture simply optimises for a different direction. A minimal TFX repository binding closes the local execution gap without turning either system into a generic division framework.

05 / Published surface

SLS feels more finished; TFX explains more of design

Both use a restrained three-rail documentation shell and both reflow without page-level horizontal overflow at 320px.

What SLS does well

  • Familiar navigation, search and on-page wayfinding.
  • Calm density, disciplined alignment and very little decorative chrome.
  • Concrete paths from guidance to packages, Storybook and skills.
  • A published surface with no obvious unfinished UI.

What TFX does well

  • A more distinctive visual and editorial identity.
  • Clear maturity signals: proposed versus settled.
  • Human and machine views generated from the same sources.
  • A richer information architecture across principles, standards, guidelines, products and governance.

Current TFX polish debt: the local Harness landing still exposes an “Illustration slot” placeholder and clips card descriptions. That makes the SLS publication feel more production-ready, even though the detailed TFX pages and underlying content model are stronger.

06 / Lineage

Visible influence, substantial independent implementation

Acknowledging an input does not diminish the work that followed. That is the most credible and constructive position.

What plausibly travelled

  • Skills encode repeatable design workflows.
  • Ambiguity is resolved before code.
  • A quality gate runs through iteration.
  • Humans confirm rendered output.
  • Anti-patterns, evals and durable decisions are first-class artefacts.

What is clearly SLS work

  • SLS documents a former @sls/builder package, so some lineage predates this exchange.
  • The token, component, Storybook, CI-preview and build-flag mechanics are deeply SLS-specific.
  • Distinctive TFX mechanisms are absent: control tiers, waivers, divergence, ratchet and an independent evaluator.

Fair conclusion: the shared TFX work likely influenced the direction or framing; SLS then built a meaningful repo-native implementation. It is reasonable to ask for a heads-up, reciprocal links and acknowledgement of inputs without claiming ownership of every underlying idea.

07 / The real risk

The risk is ownership ambiguity, not multiple harnesses

Product and engineering teams can keep their own orchestration. The unresolved question is which layer owns design quality.

SLS describes its quality gate as the authoritative quality standard for UI work in its repository. TFX is designed around one shared control catalog across products. If both define overlapping design rules without a mapping, teams will eventually receive two answers to the same question.

The failure mode is predictable: duplicated controls, incompatible waivers, conflicting evaluator verdicts, repeated investment and surprise publications that erode trust. None of this requires merging codebases.

The relationship should be explicit: TFX keeps its portable design intent and quality loop; SLS keeps its repo-native implementation. Where the systems overlap, they should map controls and evidence explicitly. Other domains can fork the TFX work and diverge rather than depending on one shared runtime.

08 / Proposed model

Shared design intent, explicit repository boundaries

Keep TFX design quality portable within the TFX portfolio. Let SLS and each TFX product own the implementation facts needed to make their local workflows real.

Shared design-quality core

TFX controls, skills, visual evidence, evaluator and governance

Defines what must travel across products and how design judgement becomes auditable.

connected through explicit mappings

SLS implementation

SLS tokens, components, Storybook, commands, CI gates and previews remain SLS-owned.

TFX repository binding

A minimal TFX-only declaration of product roots, approved checks, local routes and states.

Other domains

Fork the TFX standard when useful, then own their controls and product workflow independently.

TFX design layer

Portfolio controls, principles, domain skills, the intent-preserving loop, evaluator rubric, waivers and governance.

TFX repository binding

Execution facts only: product roots, approved package scripts, local preview routes and evidence capture. It cannot redefine controls.

Product harness

Engineering orchestration, source edits, tests, builds, deployment controls and product-specific sequencing.

Joint interface

Control mapping, evidence format, local extensions and a route for product failures to feed the TFX ratchet.

  1. Hold one architecture and governance sync

    Bring SLS and the design-skill owners together to agree what is normative, mapped and locally owned.

    High impact · small

  2. Stress-test both systems on the same brief

    Compare repo conformance, design-intent recall, journey coverage, visual quality, time and cost.

    High impact · medium

  3. Crosswalk the SLS quality gate to TFX controls

    Keep SLS-only checks as named extensions instead of silently creating a second catalog.

    High impact · medium

  4. Agree attribution and socialisation norms

    Add reciprocal links, acknowledge material inputs and give one another a heads-up before publishing overlapping work.

    Medium impact · small

  5. Borrow the strongest SLS mechanics upstream

    Prioritise a minimal TFX repository binding, preview-first work, stale-gate invalidation and isolated A/B skill evals.

    High impact · medium

09 / Suggested outreach

Start with the architecture, then address the process

The work is useful. The conversation can be direct about the missing heads-up while creating a concrete path to collaborate.

Thanks for sharing the SLS builder work. The repository integration, preview workflow and deterministic checks are genuinely strong. I was surprised to see it published without a heads-up because I had shared the TFX harness as an input. I do not think we need to merge the implementations or compete over one harness. I would like us to make the relationship between them explicit. TFX can keep its portable design controls, visual quality loop and evaluator, while SLS keeps its repository-native components and delivery tooling. Where the systems overlap, we can map controls and use compatible evidence rather than create two answers to the same design question. We could test that model by running the same brief through both systems and crosswalking the results. I would also appreciate reciprocal links, acknowledgement of material inputs and a shared norm for socialising overlapping work before publication. Could we hold a short architecture session with the relevant design and engineering owners?
